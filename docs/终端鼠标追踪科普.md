# 终端鼠标追踪与「选区模式」原理科普

> 目标读者：完全不懂终端底层机制的小白。
> 读完你能明白：为什么在某些 TUI 程序里「鼠标拖选 + Ctrl+C」复制不了，以及我们是怎么绕过去的。

---

## 1. 两个房间，一堵墙

想象有两样东西：

- **终端软件（xterm）**：你眼睛看到的那个黑框框，负责显示文字、接收你的鼠标键盘。
- **里面跑的程序（比如 pwsh、或者某个带鼠标支持的 TUI 菜单）**：真正干活的「大脑」。

它们是两个**独立进程**，互相看不到对方。它们之间只有一条**纸条通道（字节流）**可以传话。

```
   ┌──────────────┐        字节流(纸条)        ┌──────────────┐
   │   终端 xterm  │ <───────────────────────> │   程序 TUI    │
   │  (显示/输入)  │                           │   (真正逻辑)  │
   └──────────────┘                           └──────────────┘
```

程序想让终端做点特殊的事（清屏、变色、**开鼠标**），就往纸条上写一段「暗号」塞进通道。终端收到暗号，就照做。

---

## 2. 什么是「暗号」（转义序列）

这段暗号在终端世界里叫 **转义序列（escape sequence）**，固定以这样开头：

```
ESC [
```

- `ESC` 是一个固定的字节（ASCII 27，十六进制 `0x1B`），在代码里写成 `\x1b`。
- `[` 紧跟其后。`ESC[` 的意思是「下面是一句控制指令」。

我们今天碰到的这一类暗号，专门管「终端的各种开关」，长这样：

```
ESC [ ? <数字> <h 或 l>
```

把它当成一个**拨动开关的指令**来理解：

| 片段 | 含义 | 类比 |
|------|------|------|
| `?` | 这是一类「私有功能开关」 | 就像设备里预留的自定义寄存器区 |
| `<数字>` | **功能编号**，每个数字对应一个功能 | 像 PLC 里的**线圈地址 / 寄存器号** |
| `h` | 把这个功能**打开**（set） | 把线圈写 1 |
| `l` | 把这个功能**关闭**（reset，小写字母 L） | 把线圈写 0 |

⚠️ 注意：那个 `<数字>` **不是数量、不是尺寸、不是像素**，它纯粹是个「功能代号」，就像给每个开关贴了个编号标签。

---

## 3. 1000 / 1002 / 1003 到底是什么

在终端标准里，`1000`、`1002`、`1003` 这三个编号被分配给同一类功能：**鼠标上报**。

意思是：「把我的鼠标动作，变成暗号回报给我（程序），别让终端自己拿去框选文字。」

历史上终端能力逐步升级，于是有了三档：

| 程序发给终端的暗号 | 功能 | 说明 |
|---|---|---|
| `ESC[?1000h` | 开鼠标（基础档） | 只在**按下**时报告坐标 |
| `ESC[?1002h` | 开鼠标（拖动档） | 按下 + **拖动**都报告 |
| `ESC[?1003h` | 开鼠标（全量档） | **只要移动**就报告 |

不同的 TUI 程序用的档位不同，所以后面我们进/出「选区模式」时，会把这三种都照顾到，管它原来开的是哪个。

---

## 4. xterm 的「小本本」：mouseTrackingMode

当 TUI 程序启动时，它会挑上面某一个暗号发给 xterm，相当于说：

> 「把我的鼠标事件都回报给我，终端你别自己框选文字了。」

xterm 收到后做了两件事：
1. 把内部状态 `mouseTrackingMode` 记成对应的值；
2. 从此把你的鼠标拖拽**转成暗号发给程序**，而不是生成文字选区。

xterm 给这几个编号起了「人能读的名字」，方便打印：

| 编号 | xterm 记的名字 |
|---|---|
| `1000` | `x10` |
| `1002` | `drag` |
| `1003` | `vt200` 或 `any` |

所以你之前在控制台看到打印 `鼠标模式 = x10 / drag / vt200 / any`，**只是 xterm 在告诉你：「当前开着的是 1000 / 1002 / 1003 号功能」**。这就是「数字」和「名字」的对应关系。

---

## 5. 我们怎么借它实现「复制」

我们的目标：让你能在 TUI 里**用鼠标拖选文字，再 Ctrl+C 复制**。

但 TUI 开着鼠标追踪时，xterm 不让你框选（鼠标被程序吃了）。解决办法是——**趁程序不注意，直接给 xterm 发「关鼠标」暗号**，让 xterm 单方面改回「框选文字」模式。

### 进入选区模式（关掉鼠标）

往 xterm 一次性发三个「关」指令，把三种可能的鼠标功能全关掉：

```js
s.term.write('\x1b[?1000l\x1b[?1002l\x1b[?1003l')
```

`\x1b` 就是 `ESC`。三个 `l`（关）连发，管你程序原来开的是哪个，统统关。

xterm 的 `mouseTrackingMode` 变成 `none`，它不再把鼠标当「给程序的事件」，改回「让用户框选文字」。于是你就能拖选了。

### 退出选区模式（还原鼠标）

按进入前记录的那个编号，单独发对应的「开」指令，把原来的功能重新打开。例如记的是 `x10`（=1000），就发：

```js
s.term.write('\x1b[?1000h')   // 重新打开 1000 号鼠标功能
```

xterm 把 `mouseTrackingMode` 改回原来的值，TUI 的鼠标交互恢复正常。

---

## 6. 最关键的一点：暗号写给「谁」

我们 `term.write(...)` 是把暗号**喂给 xterm 自己**（相当于「模拟程序下发了关鼠标指令」）。

**没有**发给 PTY / 程序。

```
   我们写暗号 ──► xterm  (xterm 单方面关掉鼠标，改回框选)
                      │
                      ▼
   程序  ←── 毫不知情，仍以为鼠标是开着的，还在等鼠标事件
```

所以：
- 程序那边**完全不知道**鼠标被关了；
- 我们只是让 xterm 单方面不生成鼠标事件、改回框选；
- 退出时再让 xterm 单方面把功能开回去。

程序全程无感知，体验无缝衔接。

> 反例：如果把这些暗号发给「程序」（塞进 PTY 的 stdin），程序会把它当成无意义的按键输入/乱码，反而出错。正确目标必须是 xterm 自己的解析器。

---

## 7. 一句话总结

- `1000 / 1002 / 1003` 是终端里「鼠标上报」功能的**编号**；
- `h` = 开，`l` = 关；
- TUI 开着鼠标时，xterm 不让你框选；
- 我们**直接给 xterm 发 `l` 关掉鼠标** → 就能拖选 → Ctrl+C 复制 → 再发 `h` 还原；
- 整个过程程序毫不知情。

这就是「选区模式」能让你在 TUI 里复制文字的原理。
